# 邮箱验证码发送可行性评估

## 结论

技术上可行，但**当前不实现**，原因是本任务明确要求不改后端，而后端目前没有：

- 邮箱字段、邮箱唯一索引、邮箱登录接口；
- 验证码签发/校验接口；
- SMTP 或邮件服务配置（`config/settings.py` 只有账号注册开关、邀请码、token TTL）。

因此当前前端的“邮箱”只是**本机登录别名**，验证码无法真正发出，也不能跨设备用邮箱登录。

## 当前账号能力（前端-only 方案）

- 注册：邮箱 + 用户名 + 密码
  - 邮箱保存在本机 SharedPreferences，作为本机登录别名；
  - 实际调用后端现有 `POST /auth/register`，只提交 username/password。
- 登录：邮箱或用户名 + 密码
  - 邮箱先在本机别名表解析为用户名，再调用 `POST /auth/login`；
  - 用户名直接登录。
- 长期记忆：服务端聊天/记忆接口按 token 对应的 `user_id` 隔离；前端聊天历史、发件箱、反馈也按 `user_id` 分区。
- 同名用户名：后端当前用户名唯一，重复注册会返回 `username_taken`；因此同名账号无法创建。若未来后端允许同名，必须继续以 `user_id` 而不是 username 作为记忆键。

## 真正发送验证码需要的条件

### 方案 A：邮箱 SMTP（最快验证）

- 一个支持 SMTP 的发件邮箱（QQ 邮箱/163/Gmail 应用专用密码等）
- 后端配置：SMTP host、port、username、password/app password、from、STARTTLS/SSL
- Python 标准库 `smtplib` 即可发送，无需新增依赖
- 缺点：个人邮箱有频率限制、易进垃圾箱、发件域名信誉差，**不建议正式环境**

### 方案 B：事务邮件服务（推荐）

- Resend、SendGrid、阿里云邮件推送、腾讯云 SES 等
- 需要：API Key、已验证发件域名、SPF/DKIM/DMARC 配置
- 优点：送达率、退信/投诉处理、模板、日志
- 成本：通常有免费额度，按量计费

### 方案 C：自建 Postfix/Cloudflare Email Workers

- 可控但运维成本高；需要独立域名、IP 信誉、反垃圾策略，不建议当前阶段

## 推荐验证码流程（后端改造时）

1. `POST /auth/email/send-code`
   - 入参：email、purpose（register/login）
   - 生成 6 位数字，服务端只存 HMAC/SHA-256 摘要
   - 10 分钟过期；60 秒重发冷却；单邮箱/单 IP 小时级限流
   - 无论邮箱是否存在都返回统一文案，防止枚举
2. `POST /auth/register`
   - 增加 `email`、`email_code`
   - 校验邮箱唯一、验证码正确且未过期
3. 登录
   - 支持 email；邮箱必须已验证
4. 安全
   - 验证码不写日志、不返回客户端
   - 失败次数上限（如 5 次）后作废
   - 密码仍使用 PBKDF2/Argon2，token 只存摘要
   - 生产环境启用 HTTPS、限流、审计

## 阻塞项

- 不改后端 → 无法发码/验码；不能实现真正的邮箱身份。
- 没有发件域名/API Key → 即使写了发送代码也无法送达。
- 当前前端邮箱别名只在本机有效，清空 App 数据或换设备后邮箱登录失效。

## 建议

先上线“用户名+密码”的真实服务端账号（本次已完成），邮箱作为本机别名过渡；确定邮件服务商并允许改后端后，再按上面流程加验证码，届时把邮箱升级为服务端唯一登录标识。
